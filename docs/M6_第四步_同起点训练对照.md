## 1. 为什么做两个模型

179条训练chosen中，26条直接选原模型回答，153条由我这个AI修订。假如模型之后变好，可能只是新示范比较好，不一定需要DPO。

所以两条路线从同一个原M3 SFT复制：

| 路线 | 学什么 | 模型参数更新依据 |
|---|---|---|
| chosen-only SFT | 179条chosen示范 | 最后chosen回答与EOS的交叉熵loss |
| DPO | 同179组chosen/rejected | 两条答案相对冻结原SFT的偏好变化 |

两条都不从m6_dpo_smoke_01继续，不叠加旧Adapter，不改写原M3产物。两条使用相同short、输入、chosen、1轮、学习率1e-5、batch1/累积4、seed42。DPO额外使用rejected、beta0.1与参考概率。

相同179组和45次更新**不是等计算量**：DPO每组处理两条回答，还计算参考概率；SFT只处理chosen。分别记录token曝光、时间、步数与内存采样，不把不同loss数值直接拿来比较谁好。

## 2. 先看数据确实怎样进训练器


不加载Qwen、不训练。它展示一条实际偏好、SFT中参与loss的文字与DPO额外读取的rejected。

SFT：问题和历史的labels为-100，只监督最后chosen＋一个EOS；rejected没有进SFT输入和loss。DPO：两条已知答案都计算目标概率，只有最后回答＋EOS计入，问题历史只是上下文。评分数字和审核理由不作为模型提示词或loss输入。

文件的split决定用途，不是让模型读到一个叫train或dev的词。冻结文件FORMAL_FREEZE.json记录实际数量、数据/审核/候选哈希与局限；修改这些内容会使来源检查失败。

## 3. 你先启动chosen-only SFT

关闭驻留模型Demo，运行：

```bash
.venv-m6/bin/python scripts/m6_train.py train --method chosen_sft
```

这条命令才开始实际参数更新。顺序是加载原SFT → 生成step0开发回答 → 训练 → 在step15/30/45生成同6题回答 → 保存独立policy Adapter。

179组、每4组累积后更新，44组完整累积加最后3个样本，共45次更新。最后的小组不会被悄悄丢掉，临时Trainer测试已验证这种不足4的末组仍更新。各检查点的6条回答是开发生成，不参加梯度；生成会恢复模型训练状态与随机状态。

若在第15/30/45步短暂停住训练日志，可能是在生成开发回答或计算开发loss，终端会打印相应题目，不代表卡死。

完成后另开一次Python进程重载：

```bash
.venv-m6/bin/python scripts/m6_train.py verify --method chosen_sft
```

查看results/m6_formal_01_chosen_sft/development_timeline.md，保存的Adapter为outputs/m6_formal_01_chosen_sft/adapter/policy/。

## 4. 然后启动DPO

SFT进程退出后再运行，不同时驻留两条训练路线：

```bash
.venv-m6/bin/python scripts/m6_train.py train --method dpo
.venv-m6/bin/python scripts/m6_train.py verify --method dpo
.venv-m6/bin/python scripts/m6_train.py status
```

DPO先重新加载**原M3 SFT**，不是刚完成的chosen-only SFT；建立policy和冻结reference，生成step0回答，然后固定179组参考概率，才开始45次更新。step15/30/45生成同样6题并保存完整policy。

结果在results/m6_formal_01_dpo/，Adapter在outputs/m6_formal_01_dpo/adapter/policy/。两条训练都选固定一轮的最后checkpoint，不从最终测试挑模型，也不根据6组开发偏好不断试参。

## 5. 你观察什么，我评什么

训练日志：SFT loss表示示范目标概率；DPO loss、reward margin表示相对参考的偏好变化。两种loss定义不同，不能说哪种数值小就更好。各步数据批次不同，波动正常；NaN/Inf或报错保存日志交给我。

开发偏好仅6组，覆盖安慰2、学习3、稳定性1。它们的eval_loss只能作过程诊断，不能代表技术、日常、关系或整体效果。开发chosen没有被改写，质量差的24组已经拒收，不为了让数字好看降低门槛。

另6条固定生成探针覆盖六类，均为各类dev-01，和保留的6组偏好不重叠。它们已在小样本阶段及本轮审核见过，只叫开发回归，不能称未见最终测试。你可以先对比安慰题是否还责备用户、空集合题是否纠正、三汉字约束是否遵守；我负责后续系统评分，不需要你逐题打标。

口吻优劣不按hoho、姐姐或波浪号数量算。此批只有2组较弱风格偏好、1组呈现偏好，主体是事实、任务、上下文与边界纠错，不能把它包装成全面的人设偏好覆盖。

## 6. 保存、重载与失败边界

每条路线都会保存training.json、training_log.json、development_timeline.json/.md、来源快照、checkpoint和完整policy Adapter。DPO另有reference_probabilities.json；缓存绑定当前数据、模型、提示词、代码与版本。

verify在新进程核对文件、设备、精度与数值探针。探针差0证明该输入下加载一致，不是回答正确率100%。原SFT文件保持不变，reference逐tensor检查不变，基础权重通过冻结梯度及预测探针核查；不把一条探针说成全模型数值证明。

本入口不支持中断checkpoint恢复。中断保留已经保存的日志与checkpoint，交给我定位后另建run；不删除旧记录原地重做。成功run重跑train会核对产物并退出，不重复更新。新的参数尝试必须使用新的run_prefix，不能覆盖这两条路线。

配置已固定在configs/m6_formal.json。不要为了继续训练直接修改当前run的epochs或数据路径；修改条件后不能再用旧run宣称复现。

## 7. 源码阅读与回顾

主链：main → preflight/validate_rows核对冻结数据与实际审核 → make_model精确复制原SFT → make_trainer分别构造SFT或DPO目标 → observe(step0) → Trainer.train → Progress.on_step_end每15步生成 → 参数/来源检查 → 保存policy → 新进程verify。

必读scripts/m6_train.py的sft_rows、make_trainer、train及其Progress回调，再读verify；参考scripts/m6_dpo.py的make_model、copy_reference_from_policy、trainer_class和observe。旧小样本与采样源码不改，新的正式入口独立保存自己的来源。

失败分支：输入/审核哈希不符时训练前停止；已有未完成run不自动恢复；训练或生成报错留下progress与日志；参考参数变化、非有限指标、更新次数不符或重载不一致都会报错，而不是标完成。

回顾：指出SFT里rejected是否参加loss；解释为什么DPO不从chosen-only SFT继续；说明45步怎样计算；对比6题的四个时点，分别记下改善、未变与退化，不用loss下降代替质量判断。
