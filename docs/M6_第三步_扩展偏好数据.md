# M6第三步：扩展训练与开发候选

本课操作已完成：学习者生成420条候选、失败0，助手审核210题并导出179组train、6组dev，训练拒收1、开发拒收24；原20组不变。数据冻结与局限见[审核总结](../results/m6_preparation/reviews/expansion_report.md)。继续[M6第四步](M6_第四步_同起点训练对照.md)，以下保留本课操作与原理。小样本DPO仍是5次更新与重载通过，6题观察未显示明确整体改善。

## 1. 这一步输入和输出是什么

输入仍是冻结的short角色提示词＋预先划分的新问题／历史。候选仍由**原M3 SFT模型**生成，每题两条。这一步不加载刚训练的DPO Adapter，不更新任何参数。

目标覆盖180个训练问题、30个开发问题：

| 集合 | 已生成 | 本次新增 | 最终候选数 |
|---|---:|---:|---:|
| train | 20题、40条 | 160题、320条 | 180题、360条 |
| dev | 0 | 30题、60条 | 30题、60条 |
| test | 0 | 0 | 60题继续封存 |

总共420条候选，当前已有40条，本次最多新增380条。这里的180/30是待审核场景数量，不保证审核后恰好得到180/30组可用偏好；生成失败、同文、平局和两边都差都可能减少数量。

**train给模型学习；dev帮助我们检查和选择训练方案；test留到方案固定后做最终评测。** 把dev或test也拿去训练，就不能再用它们说明对新问题的表现。

## 2. 你现在运行的第一条命令

先关闭聊天Demo和其他驻留模型进程。在项目终端执行：

```bash
cd "/Users/jakiimo/Desktop/AI Waifu"
.venv-m6/bin/python scripts/m6.py collect --split train --limit 180 --resume
```

- `--split train`：只采样训练区。
- `--limit 180`：覆盖训练区前180题，**不是额外增加180题**。
- `--resume`：核对并保留已完成的前20题，只生成缺少的320条候选。

因此通常从`41/360`继续显示。原来40条不会重写，也不会重新随机采样；第一批20组偏好和小样本DPO产物保留。

采样次数比上一批多，耗时受回答长度与机器状态影响。每条候选都会即时保存，不必一直盯着终端。Ctrl+C中断后可重跑同一条带--resume的命令。已保存的生成错误不会自动变成成功，别删除错误行后重跑来掩盖问题。

## 3. 再生成开发候选

训练候选采样进程退出后，再依次运行：

```bash
.venv-m6/bin/python scripts/m6.py collect --split dev --limit 30 --resume
.venv-m6/bin/python scripts/m6.py review-pack --split train
.venv-m6/bin/python scripts/m6.py review-pack --split dev
.venv-m6/bin/python scripts/m6.py status
```

开发采样仍用原M3 SFT。train/dev命令顺序运行，不同时开两个M6采样进程。原始记录保存在同一个candidates.jsonl中，每条带split字段，训练与开发仍明确分开。

没有生成错误时，status应显示train候选360/360、dev候选60/60。**审核记录此时仍是20**，因为新采样还没经过我的审核；候选齐备不等于偏好数据齐备。最后一句旧提示“收集小批候选”来自冻结采样脚本，表示该脚本的职责，不表示已完成的小样本DPO被撤销。

review-pack会打印两个内容哈希命名的审核包。train新包通常包含全部180题，dev包含30题；前20题虽然再次出现在新包里，我会保留原审核决策，避免重复标注。旧20题审核包保留；原决策仍绑定旧包及原始候选版本。

到这里把终端最后的状态与两个审核包路径发给我即可，不需要逐题评分或手工改JSON。我将读取本地文件，分批实际审核。

## 4. 我将怎样审核

固定规则仍为voice口吻、persona_context情境人设、usefulness有用性三维。先保证事实、要求、帮助和边界，再看俏皮程度；不靠“hoho”“姐姐”或波浪号的数量选赢家。

训练区：有合格原候选就选择；两边都差时拒收，或明确写出AI修订chosen并记录来源。rejected保留实际候选。已审核的20组不覆盖。

开发区：依照PRD，只在合格原候选间选择清晰偏好，否则拒收；**不改写开发chosen来凑30组**。技术题核查代码结果或官方资料。实际留下的开发偏好太少时，再决定是否需要单独扩展开发候选版本，不把坏答案标成好答案。

报告区分事实/帮助/约束纠错对与主要口吻不同的风格对。如果几乎没有“两边任务都合格、主要口吻不同”的配对，就不能把这批数据说成充分覆盖风格偏好；先记录缺口，再补相应数据。

审核会记录接受、修订、拒收数量、六类分布、失败类型、chosen/rejected长度关系与评分来源。左右位置随机，重要或疑难配对交换复核；同一AI上下文的复核不冒充独立双盲。全部AI反馈，不称人类标注。

第一轮小样本的6个开发问题已经用于观察，后续仍可以作为开发回归题，但不能称未见最终测试。正式对照会明确开发偏好与生成探针的用途；测试60题继续封存。

## 5. 为什么还要做chosen-only SFT

我们第一批18条chosen是新修订示范。若之后模型变好，可能是这些新示范教得好，也可能是DPO的对比目标起作用，需要一个对照才能区分。

```text
                      同一份原M3 SFT起点
                         /          \
              只学习chosen        学习chosen/rejected相对偏好
              chosen-only SFT                DPO
                         \          /
               同样的新问题、同样的short提示词进行对照
```

两条训练路线都从原M3 SFT副本初始化；不是一条从小样本DPO继续、另一条从原SFT开始。记录实际样本曝光、步数、token量与耗时，不宣称两种目标天然等算力。完整配置和训练命令要等审核数据就绪后提供，由学习者启动。

选读tests/test_m6_preference.py的恢复、test禁入与审核门槛用例。暂缓新的正式训练器和PPO，本课先完整走通“候选→审核数据”这条流程。

例如从180题命令开始：前40个key已存在而跳过；下一题用同一short与原SFT采样；保存后再采下一条；中断只影响未保存部分；恢复仍用相同输入和seed。全部候选齐备后生成新包，审核后才成为训练数据。
